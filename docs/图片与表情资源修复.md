# 图片与表情资源修复

## 2026-09-27 根因与实现

普通图片的本地资源为微信 V2 DAT，原解码器只支持旧式单字节 XOR。新增 `agents/media_images.py`，支持明文图片、旧 XOR、V1 与 V2 分段解码；校验文件长度、AES padding 及图片解码结果。缺少参数、分段损坏和解码失败分别记录错误，不能将占位发送成功视为图片成功。

macOS 的 V2 参数推导默认关闭。只有用户授权后，才在本机运行配置中设置 `macos_image_key_derivation: true`；Worker 根据本条媒体路径所在账号，读取已知 kvcomm 缓存文件名，在内存中派生候选并验证图片。不会扫描进程、修改微信、打印或持久化参数，也不扫描其他工具的私有密钥目录。不支持此布局或候选无效时保留失败项，不能保证所有微信版本均适用。

参考格式与参数说明：[V2 文件结构](https://github.com/jackwener/wx-cli-again/blob/main/src/attachment/decoder/v2.rs)、[macOS 参数派生](https://github.com/jackwener/wx-cli-again/blob/main/src/attachment/image_key/macos.rs)。本项目独立实现，未安装或执行上述工具。

表情发送记录可能只有 md5，没有 CDN 地址。Worker 先检查消息 content/text 中的 XML、已有下载地址与读取器返回的本地资源；仍不可用时，通过现有微信 CLI 在同一群内检索同一 md5 的原始记录，最多读取 100 个匹配结果。仅接受群身份与摘要一致的候选，并在有有效摘要时校验下载内容。资源不可得、查询失败、下载失败、摘要不符和解码失败有独立错误码；不在日志中输出原始下载地址。

表情继续保持最大 200×200、等比缩小、不放大。GIF、动态 WebP 等多帧资源输出 GIF，单帧输出 PNG；限制下载大小、帧数和总解码像素。历史无匹配、地址失效且本地没有可读资源时仍可能失败，会保留人工处理记录。

## 2026-09-28：复发图片的附件索引与 WXGF 修复

新的失败样例与此前 V2 密钥问题不同，存在两层遗漏：

1. 消息正文中的图片 md5 在 hardlink 索引中没有条目；实际文件以消息 `packed_info_data` 中的附件标识命名，位于当前账号、当前群的 `msg/attach/<群摘要>/<月份>/Img/`。原读取器因此返回空列表。
2. 文件 V2 解密成功后为 WXGF/HEVC 图片，原先的 JPEG/PNG/GIF/WebP 校验将它归为解码失败。不是本机密钥重新失效。

新增只读 `image-resource` 扩展，通过群、local_id、create_time、server_id、消息类型核对源记录，按 protobuf 明确字段读取附件标识。只接受同群目录下精确名称的 `.dat`、`_h.dat`、`_t.dat`，不按发送时间接近、同名文件或跨群缓存猜图；缩略图单独标注。扩展随 `install_reader_sync.py` 安装并保留回滚备份，不修改微信数据库。

WXGF 静态图片由现有本机 FFmpeg 转为 PNG，转换前限制尺寸，转换后验证格式、完整性及原始尺寸；最多读取两帧以拒绝静默截取动画。转换失败、缺少 FFmpeg 或遇到不支持的多帧格式时，沿用明确标注的缩略图回退，仍无可用资源才保留失败项。参考作者的一手格式分析：[WXAM（WXGF）图片格式解析](https://www.harvey.eu.org/posts/wxzm)，本项目独立实现，不运行第三方取密钥程序。

验证：新增附件定位与隔离、错误身份、损坏字段、符号链接越界、原图失败回退缩略图，以及合成 HEVC 真实转换、尺寸一致、缺少转换器、多帧拒绝等测试。本次完整 QA 250 项通过（含界面与接口探针）。真实失败文件在本机转换为 1220×2812 PNG，完整加载校验成功；这是当前格式及样例的证据，不代表所有微信媒体格式均已覆盖。

部署后真实验证：三组已运行绑定恢复正常。原失败图片经正式重试上传成功，一次尝试；飞书回读为 image 类型，目标群正确，reply_to 为原占位消息。用户仍需目视确认图片展示；不自动补发其他历史失败项。

## 2026-10-01：#36 普通图片的质量降级与补原图

本次为 macOS 15.3.2、微信 4.1.15（270095）、读取器 0.9.2-preview.2 上的普通图片。对照源文件创建时间、发送回执以及下载回读的图片字节：飞书收到的是 180×106、5829 字节的预览，摘要与本机缩略图相同；可解码的高清资源为 1350×790。原图缓存比缩略图上传开始晚约 0.4 秒到达，本次首次降级有依据，不是飞书把已上传原图压成缩略图。普通 DAT 候选包含不支持的 WXGF，但高清候选可以正常解码，不能把本例直接归为密钥失效。修复后的本机流程已再次完整解码为 1350×790 PNG，`thumbnail_only=false`，外发次数为零。真实原文件、回执、路径和身份只保存在本机私有诊断目录。

另外通过隔离测试确认两处遗漏：普通媒体索引只有缩略图时不会再查询精确附件索引；索引中原图损坏时，可能直接回退预览，漏掉附件索引的可用原图。修复后在这两种情形补查现有 `image-resource`，仍严格匹配群、local_id、server_id、create_time 和契约，不靠大小或时间接近猜图。已有可用原图时不额外轮询等待。

普通图片首次上传前保存所选质量、内容摘要及私有发送快照。发送结果不确定时复用原字节和去重标识；快照丢失或变化、超过去重窗口时停止该补发并等待人工核对，不能改用后来缓存的另一份图片冒充原重试。仅有预览或原图不可解码时仍如实标注；质量原因与待办一起保留。若先前只发了资源占位，人工补发得到缩略图时会单独标注清晰度，不重复署名。明确被拒绝的上传允许更新安全的本地文件路径和恢复过期快照，保留原目标和去重标识；从缩略图升级为原图时补充质量说明。

### 使用方法

1. 新产生的缩略图成功投递后，自动在管理台「失败与补发」登记「补原图」待办；登记本身不排队发送，也不阻塞后续正常消息。
2. 在本机微信打开并下载该条原图，点击管理台「补原图」并确认。也可告诉 Codex 按待办编号执行 `python -m agents.manage media-failures retry --id <待办编号>`。运行中的对应 Worker 才会处理；不会自动启动已停止的 Worker。
3. 成功后，只把原图回复到已送达的图片；保存独立回执，不重发署名、正文或缩略图，不改写原消息的姓名快照和游标。重复处理复用成功回执。仍只有缩略图时保留待办，不再外发；上传失败按现有最多三次一轮的策略处理，之后仍可人工发起新一轮。
4. 升级前的普通图片没有质量待办，先核对真实图片和成功回执。执行 `python -m agents.manage media-failures original-image --id <数据库消息编号>` 可单独登记历史待办；这个编号不是微信 local_id，也不是待办编号。登记仍不发送，需另行点击「补原图」。不批量扫描或重发历史图片，不回退游标。

## 补充：短暂等待与有限次自动补原图

用户已同意默认采用“短暂等待 → 缩略图兜底 → 有限自动补原图”。以下替代上节新消息必须手动补原图的默认策略；升级前的待办仍保留人工处理。

- 普通图片先使用现有读取器查找原图。若只有可用缩略图，保留私有快照并额外等待最多 5 秒，间隔约 1 秒重新检查；补查 CLI 共享剩余等待预算，等待结束即使用缩略图。已有可用原图不等待。首次正常读取和图片解码仍受各自原有超时约束，5 秒是额外等待窗口，不是整条消息的端到端耗时承诺。等待截止时间持久化，暂停恢复不会再从头等待 5 秒。
- 缩略图确认送达后，在同一 SQLite 中自动登记原图任务。首次 30 秒后检查，随后分别间隔 120 秒、600 秒，各一次，共最多三次（包含资源查找或上传失败）。群里没有新消息也会唤醒现有 Worker，不依赖 600 秒源消息轮询；不创建额外守护进程、开机任务或自动重启。
- 图片稍后缓存成功时，自动补发原图，回复已有图片，复用先前已验证的独立回执与冻结快照逻辑。结果不确定时复用同一内容和去重标识；超过去重窗口、无法核验快照时提前转人工。原图缺失或上传失败达到上限后保留“补原图”待办，之后可明确发起人工重试。
- 检查次数与完成时间保存在数据库，重启不会重置；中断发生在状态提交与调度更新之间，也按已保存的完成时间计算下一次检查。暂停或停止时不发送，读取过程中暂停不消耗次数。恢复后继续剩余次数，不集中补跑所有错过的检查。
- 管理台「失败与补发」显示等待中的任务、已尝试次数和下次检查时间；自动任务或已排队任务的按钮禁用，避免重复排队。绑定暂停/停止时显示的时间是任务到期时间，实际执行需绑定恢复。
- 只为新确认送达的缩略图建立自动任务，不批量扫描或补发历史图片，不将已有人工待办重新改成自动任务。历史图片仍先核对，再通过原有 `original-image` 登记并人工补发。

本机运行配置可设置 `image_original_wait_seconds`（默认 5，可设 0 关闭等待，上限 5）和 `image_original_auto_retry`（默认 true，false 关闭自动补原图）。配置修改需由 Codex 明确重启对应 Worker 后生效；关闭自动补图会把尚未完成的自动任务转为人工待办，不删除记录。管理台保存其他配置会保留这两个本机设置。

本轮仍仅做隔离测试和代码修改，不重启生产 Worker、不外发真实图片、不自动处理此前的真实待办；#36 的真实飞书图片验收仍待明确授权后进行。
