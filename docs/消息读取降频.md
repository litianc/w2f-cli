# 消息读取降频与通知合并

## 已确认方案

每组完整源消息扫描的开始时间至少间隔 10 秒；轻量变化监听继续每秒工作，期间重复通知合并为一次待处理扫描。只合并检查请求，按原游标完整读取、顺序发送所有新消息，保留 600 秒正常兜底检查。

## 调度行为

- 每条绑定独立调度，不引入新守护进程。首次启动立即读取，异常退出仍由用户通知 Codex 恢复。
- 读取间隔从扫描开始计时，连续通知不延长截止时间。扫描期间出现的通知保留，下一轮按最小间隔处理。一次离线补扫的分页和发送仍连续进行，不在每页或每条消息间等待 10 秒。
- 发现并发送了新消息后，下一轮检查也遵守最小间隔；没有通知且没有新消息时，按 600 秒兜底。若配置的兜底间隔短于最小间隔，最小间隔优先。
- 暂停时不读取、不发送；恢复时请求扫描并保留当前进程的剩余等待窗口。重启使用已有游标，立即进行首轮补扫。连续错误保留原有退避，变化通知不能绕过它。
- 图片、文件补发使用单独的到期时间，不再借补发触发整群扫描。自动补发沿用原次数和间隔；SQLite 每隔至多 5 秒检查人工新增的补发任务。停止或暂停的绑定不执行任务。
- 控制状态每隔最多 0.5 秒检查，保持暂停、停止响应；心跳沿用 5 秒周期。最小间隔是源扫描开始之间的限制，消息总延迟还包含读取、网络上传和正在处理的积压。

本机运行配置新增 `source_min_interval`，默认 `10`，单位秒，可设为 `0` 关闭降频，允许范围 0～600。与 `poll_interval: 600` 配合使用，由 Codex 修改运行配置并明确重启 Worker 后生效；管理台保存其他设置时保留该值。无需重设绑定或回退游标。

## 验收

1. 连续通知不会使同一绑定提前扫描，也不会无限延后扫描。
2. 扫描期间出现的新通知会触发后续扫描；窗口内多条消息按游标完整、按序送达，不重复。
3. 无通知时仍按兜底间隔扫描；一次积压分页不受每页降频影响。
4. 暂停恢复、异常重启保持游标；一组绑定的等待不阻塞其他组。
5. 媒体补发按自身到期时间执行，无新消息时补发不启动额外整群扫描。
6. 失败退避不会被通知打断；管理台保存配置不丢失读取间隔。

测试使用独立 SQLite、合成消息和替代远端发送，覆盖真实 Worker 循环及调度边界。上线后只读采样 Worker 与读取子进程的 CPU、扫描次数及开始间隔。消息活跃程度会影响样本，不能将安静时段和繁忙时段的 CPU 比值当作同负载节省率。
