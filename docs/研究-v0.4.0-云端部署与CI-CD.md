# v0.4.0 云端部署与 CI/CD 可行性研究

日期：2026-10-04（Asia/Shanghai）。对应：[核实所选云服务器的端口路径与 CI/CD 自动发布可行性](https://github.com/litianc/w2f-cli/issues/44)。研究分支 `research/v040-cloud-deployment`，基于 `codex/v0.4.0` 的 `cdf49b20c41ee02eada256fd424bd924e260b36a`。

## 结论

**这台服务器具备承载有限原型和容器发布的基础条件，CI/CD 方案可行；还不能认定已具备直接上线条件。** 建议 GitHub 托管 runner 测试并构建 → 私有 GHCR → 受限 SSH 发布 → 独立 Compose project。云端应用、专属运行资源与发布流水线尚未实现；公网13000→内部3000已实测，HTTPS入口、容量预算和发布凭据仍需落实。用户已同意推送codex/v0.4.0且测试通过后自动发布。

用户已确认真实 macOS 客户端→云→独立飞书测试群，macOS/Windows 都开发且 macOS 先实测；管理员集中管理、按用户隔离、历史浏览；使用独立飞书应用和测试群。既定存储方向是 Postgres 消息、磁盘媒体、先落库再 ack。见[产品规格](产品终局Spec.md)和[需求地图](https://github.com/litianc/w2f-cli/issues/37)。

本次主要为只读检查，并按用户端口验证要求执行一次有界临时HTTP探针，完成后已关闭。未安装软件、部署应用、改SSH/代理/防火墙、写远端文件、清理磁盘、配置Secrets或发送飞书消息。没有读取私钥、容器Env或完整业务配置。

## 实测环境

来源：用户指定的 `ssh -p 40022 root@120.133.41.177`。使用 BatchMode、连接超时和严格主机密钥校验，已知 host key、公钥认证成功。

| 项目 | 2026-10-04 实测 |
| --- | --- |
| 系统 | Ubuntu 22.04.5 LTS，x86_64，8 个逻辑 CPU |
| 内存 | 总量15 GiB，约6.0 GiB available，无swap；仅采样值 |
| 磁盘 | 根盘177 GiB、已用152 GiB、90%、可用约19 GiB；不能视为永久媒体容量已满足 |
| 工具 | Docker28.4.0、Compose2.39.2、Caddy2.11.2、Python3.10.12 |
| 共存服务 | 9个运行容器；既有Postgres14、Redis及其他业务；不得清理或重启这些服务 |
| SSH入口 | 公网40022实际会话落到172.16.0.4:22；内部sshd只监听22 |
| 网络 | 主网卡172.16.0.4/24，网关172.16.0.1；另有WireGuard接口 |
| 代理 | Caddy运行配置有 :80、:1700监听、多站点host和本机/跨主机上游；现有配置需保留 |
| 数据库 | 既有Postgres在127.0.0.1:5432；不复用既有业务库/凭据 |
| 防火墙/NAT | UFW inactive，iptables INPUT默认ACCEPT；可见NAT主要为Docker映射，未见40022→22规则；上游安全组/转发规则未知 |

主机已占用的TCP端口包括22、80、1700、3300、4100–4106、5000、8010、27017及若干仅本机端口；采样时没有443监听。内部监听不代表公网可达。Caddy仅提取listen/host/dial字段，未保存既有业务配置正文或无关域名列表。

SSH中途数次在认证前被关闭，诊断banner为 `Exceeded MaxStartups`；后续合并检查又成功。有效参数为 `maxstartups 10:30:100`、`maxsessions 10`、`logingracetime 120`。这与未认证连接限制相符，但流量来源尚未知；不是密钥缺失的证据。正式发布需有限退避重试和幂等发布标识，避免“远端已执行、回执丢失”导致重复迁移。[OpenSSH MaxStartups](https://man.openbsd.org/sshd_config#MaxStartups)

### 端口映射：13000 → 3000 已实测验证

用户补充“13000→3000，好像是1xxxx→xxxx”后，仅检查这对端口：

| 检查 | 结果 |
| --- | --- |
| 本机直连公网 `http://120.133.41.177:13000/` | TCP已连接，HTTP空回复，curl52/HTTP000 |
| 服务器 `ss -ltn` | 没有3000监听 |
| 服务器 Docker 发布端口 | 没有发布主机3000 |
| 服务器 `http://127.0.0.1:3000/` | Connection refused，curl7/HTTP000 |

初次只读检查说明3000当时无既有TCP监听，尚无法验证映射。随后在单次SSH会话中独占绑定0.0.0.0:3000，运行内存HTTP响应器：只在随机路径返回48字节随机校验串，其他路径404；不读取文件、没有凭据或业务数据；设单调时钟40秒上限与请求超时，匹配请求后提前退出。

从本机禁用代理访问公网13000的该随机路径，curl退出0、响应串完全一致；远端记录匹配成功后关闭监听。同一会话随后用ss确认 `PORT_3000_LISTENING_AFTER=False`，SSH退出0。**公网13000→这台服务器3000的数据路径已验证，临时探针已清理。**

这一结果只证明该端口对，并不揭示网关/NAT具体实现，也不能推广为所有“1xxxx→xxxx”。目前验证的是无敏感内容HTTP；实际云端仍需确定域名/HTTPS。部署前再次确认3000未被其他进程占用。

本机对公网裸IP80得到HTTP空回复，443 TLS握手失败；它们不能归因到该VM，带域名/SNI的现有路由也未验证。服务器自身127.0.0.1:80返回200。

云主机HEAD请求 `https://ghcr.io/v2/`、`https://api.github.com/`、`https://open.feishu.cn/` 分别得到405、200、404，TLS均完成：仅说明出站DNS/TCP/TLS/HTTP初步可用，不证明私有镜像拉取、GitHub runner入站SSH或鉴权飞书API已验证。

## 公网入口需要的信息

已知13000→3000可通；后续如需其他端口，需要提供方控制台中的**公网TCP端口→172.16.0.4内部端口映射表/可用范围**。当前主要还需专属域名网关的上游配置位置与TLS终止位置。优先沿用已有HTTPS网关新增专属路由；否则使用明确映射和专属域名。若只能提供高位公网端口，客户端base URL应显式包含端口，证书可评估DNS challenge。

Caddy默认HTTP challenge要求公网80，TLS-ALPN要求公网443；改变内部端口不能改变CA访问的标准端口。DNS challenge无需开放入站端口，但要求管理域名DNS；它解决证书验证，不替代业务网络入口。[Caddy ACME challenges](https://caddyserver.com/docs/automatic-https#acme-challenges)

## 最小实现建议（均待实现）

1. **测试与制品**：PR只跑隔离QA；可信v0.4.0分支通过测试后在托管runner构建linux/amd64镜像，标记commit SHA，上传私有GHCR。用GITHUB_TOKEN最小权限，actions固定commit SHA；服务器只拉取和运行，不现场构建。[GitHub发布镜像](https://docs.github.com/en/actions/tutorials/publish-packages/publish-docker-images)
2. **触发与串行发布**：用户已同意推送codex/v0.4.0且测试通过后自动发布；使用固定concurrency group、cancel-in-progress=false，部署该次构建的digest。手动workflow_dispatch要求workflow文件存在默认分支，不能只在开发分支写入就承诺能手动触发。[部署控制](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/control-deployments)、[workflow_dispatch](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#workflow_dispatch)
3. **受限SSH**：独立部署账号/key，经40022调用管理员持有的固定发布入口，限定包名/digest/操作，固定已核实host key。用command=和restrict限制key；不把现有root私钥放入CI。docker组具备root级能力，单换非root用户名不足以隔离。[OpenSSH key限制](https://man.openbsd.org/sshd.8#AUTHORIZED_KEYS_FILE_FORMAT)、[Docker权限](https://docs.docker.com/engine/install/linux-postinstall/)
4. **GHCR认证**：CI使用GITHUB_TOKEN推送；主机私有包拉取需要独立授权，通常为必要read:packages的classic PAT。按digest部署，认证材料与SSH/飞书分开。[GHCR认证与版本](https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-container-registry)
5. **资源隔离**：专属Compose project（建议w2f-v040）、网络、应用入口、Postgres容器/角色/持久卷、媒体目录、配置、日志和备份；不复用现有业务数据库或main运行数据。持久卷跨容器版本保存；不运行全机prune或删除卷的发布命令。[Compose命名](https://docs.docker.com/reference/compose-file/version-and-name/#name-top-level-element)、[volumes](https://docs.docker.com/engine/storage/volumes/)
6. **健康检查与恢复**：发布前检查容量、镜像、配置与迁移；Compose等待数据库healthcheck和应用readiness，发布后再测公网入口及版本。保留前一digest，应用失败可回退；迁移采用向后兼容增量。镜像回滚不等于数据库回滚，数据库和媒体须独立备份并验证恢复。[Compose健康依赖](https://docs.docker.com/compose/how-tos/startup-order/)、[up --wait](https://docs.docker.com/reference/cli/docker/compose/up/)、[Postgres备份](https://www.postgresql.org/docs/current/backup-dump.html)

容量预算应覆盖新旧镜像、数据库/WAL、媒体及备份；剩余19GiB适合受控测试，不等于永久存档容量足够。优先专属Postgres容器；若资源约束迫使共用既有进程，至少全新DB/角色/连接预算，不能复用既有库/凭据。Python venv+systemd亦可行，但已有Docker/Compose且宿主Python与CI不同，原型优先容器，不并行维护两套发布方式。

本机SSH成功不证明GitHub runner来源可访问；标准托管runner地址范围会变化。实现时先做无发布副作用的runner preflight，受源地址限制时再评估固定出口或受控出站拉取部署。[GitHub runner网络](https://docs.github.com/en/actions/reference/runners/github-hosted-runners#ip-addresses)
