# v0.4.0 云端文本投递（M2）

M2 在独立临时环境验证实际客户端、HTTPS API、Postgres 和发送器；出口是实现飞书 HTTP 协议的模拟服务。真实服务器发布和飞书接收核对属于 M3，Mac 实采属于 M4。

## 配置和启用

先按[端云接入操作](v0.4.0-端云接入操作.md)创建独立用户、设备、源群绑定。新绑定默认不发送。Compose 新增 `sender` 角色，与 `app` 使用同一镜像；只有 sender 挂载飞书凭据，没有管理员密码，也不读取本机 CLI Profile。

专用状态目录中的 `secrets/feishu_apps.json` 由运维管理，初始化为空对象。结构如下（使用实际所属用户和专用应用，示例值不可直接使用）：

```json
{
  "cli_EXAMPLE": {
    "user_id": "所属用户的 UUID",
    "app_secret": "专用应用的 secret"
  }
}
```

秘密目录由运维独占；文件需对容器 UID 1040 可读，与同目录数据库密码采用相同权限边界。秘密不写进 Git、命令行、客户端配置或证据。更新文件后重建 sender 以重新挂载；保留同一应用身份，逐个核对用户归属。

下列命令在当前环境的 app 容器中执行，Compose 的 `--env-file` 与 `-f` 必须指向专用 v0.4.0 环境：

```sh
python -m cloud.manage delivery-target --binding BINDING_UUID --app-id cli_EXAMPLE --chat-id oc_EXAMPLE
python -m cloud.manage delivery-status --binding BINDING_UUID
python -m cloud.manage delivery-resume --binding BINDING_UUID
python -m cloud.manage delivery-pause --binding BINDING_UUID
```

`delivery-target` 仅配置目标，不启用发送；目标一经配置不能改指其他应用或群，避免积压误投。每次获取 token 前校验应用属于绑定的用户。暂停不会撤回在途请求；已发出的请求仍应保存回执，之后不领取下一部分。停用用户、设备或绑定同样阻止新请求。

状态命令返回绑定开关、暂停原因、最多 100 条任务和 1,000 个部分的状态、固定请求 ID、尝试次数与飞书消息 ID，不返回秘密或消息正文。顺序为旧消息在前；更长历史通过已有消息查询定位事件。整条任务只有所有部分取得回执后才为 `sent`。

## 失败与恢复

| 结果 | 行为 | 操作 |
| --- | --- | --- |
| 限流 | 保存下一次尝试时间，保留请求和 UUID；同群后续消息等待 | 等待退避；其他绑定照常 |
| 明确拒绝 | 保留失败部分，暂停该绑定 | 排除机器人权限等原因后 `delivery-resume` |
| 响应丢失、缺回执、服务错误、发送中或未识别错误 | 标记结果未知，窗口内重用原请求、UUID | 查询部分状态和实际飞书接收情况 |
| 未知结果超过安全窗口，或检测到时钟倒退 | `unknown_expired`，停止该绑定，保留未完成数据 | 人工核对；普通恢复命令会拒绝，无自动跳过或换 UUID 重发 |
| 应用凭据缺失或归属不符 | 暂停，发送请求不会发出 | 修复专属凭据再恢复 |

飞书官方承诺相同 UUID 在一小时内至多成功发送一条；本实现将自动重试窗口保守设为从最早未排除的发送尝试开始 **3,500 秒**，为网络传输预留余量。后来的明确拒绝不能抹去较早的未知结果。每个已确认部分永不自动重发。参考[发送消息](https://open.feishu.cn/document/server-docs/im-v1/message/create)和[应用访问凭证](https://open.feishu.cn/document/server-docs/authentication-management/access-token/tenant_access_token_internal)。

当前没有未知过期结果的自动对账/修复命令；必须保留暂停，不能直接改库伪造成功。真实飞书回查及受控对账流程将在后续联调中完善。

## 进程和发布

sender 以 PostgreSQL 会话锁独占一个绑定，锁覆盖实际 HTTP 请求；每次请求前提交发送意图。连接丢失后该进程不能重连提交旧回执或继续发送下一个部分。进程重启读取持久状态，已确认部分直接跳过；未确认意图按未知结果规则恢复。终止信号停止领取新工作，给在途请求保存结果的机会。

四个产品服务为 `gateway`、`app`、`db`、`sender`。sender 限制 256 MiB / 0.5 CPU，空闲每两秒扫描；健康检查验证进程心跳、镜像版本和投递 schema。发布先停止旧 sender，再替换两个业务角色，验证两者镜像和健康状态；失败回退到已记录的健康镜像。核心 schema 仍为 1，新增独立投递 schema 2，仅做增量迁移。

当前线上三服务配置尚未升级。**M3 前必须受控同步 Compose、发布脚本和秘密文件，并保留旧三服务配置以回退到 M1 镜像。** 新四服务配置不能直接启动没有 `cloud.sender` 的旧镜像。镜像回退保留数据库，并不恢复数据库备份；恢复备份仍需要已有世代切换及对账流程。
