# Agent 驱动的微信到飞书群镜像同步计划

## 1. 目标与已确认约束

在当前 Mac 上由 Codex 作为管理 Agent，负责启动前检查、运行控制、身份确认、失败排查和状态反馈；由独立的 Python worker 持续执行消息采集与镜像。

底层复用现有的 `rion-wechat-cli` 和 `lark-cli`，实现单向同步：微信 → 飞书。微信 Reader 是只读的，因此不实现飞书 → 微信回写。

已确认约束：

- 已取得微信群成员同意同步聊天内容。
- 建立独立的微信身份映射系统；遇到未知或不确定的人员或 ID 时，Agent 尽快请求用户确认。
- 飞书消息只显示发言人姓名和内容，不显示发送时间，不添加“微信镜像”标签。
- 图片、视频、文件等媒体尽量原样上传；失败时允许占位、排队和重试。
- 默认先支持一个指定微信群、上线后的新消息和人工确认的飞书成员名单。

## 2. Agent 管理层

Agent 负责：

- 启动前检查并管理微信 `tail --follow` worker；worker 自己负责运行期间的读取重连和心跳。
- 维护同步游标、去重记录、重试队列和运行状态。
- 发现未知发言人时向用户发起确认。
- 调用飞书 CLI 建群、邀请成员和发送消息。
- 处理断线、重复消息、消息乱序、飞书限流和媒体失败；需要判断的异常通过管理流程交给 Codex。
- 提供状态查询、暂停同步、重新发送和补偿扫描等操作。

首次配置时完成一次性自动同步授权；之后在已授权的群和成员范围内自动发送，不逐条询问。Agent 只在身份不确定、权限变化或需要人工决策时打扰用户。

### 已确认的运行方式

- 同步 worker 使用 Python 实现，由 Codex 负责按用户指令启动、停止、暂停、恢复和查询；暂不配置 LangChain 或 `launchd` 开机启动。
- 用户发现进程退出或异常后，告知 Codex，由 Codex 检查状态并重新启动；当前不做无人值守的自动拉起。
- worker 启动时获取绑定级互斥锁；已有进程时拒绝启动。SQLite 中同时保存进程租约和心跳，状态查询可识别存活、失联和陈旧进程。
- 暂停时停止消费新的微信消息并保留游标；恢复后从最后成功位置继续，依靠消息幂等键避免重复。
- 具体操作命令和输出格式见《微信飞书镜像 Agent 运行规范》。
- Codex 在用户发起启动或维护会话时执行检查、控制和结果核验；启动完成后由 Worker 持续同步并记录状态。目前不包含自动唤醒 Codex 的机制。飞书身份确认回复由已授权的管理入口接收并关联到待确认事项，歧义交回用户澄清。

### 借鉴调研后的管理流程

- 日常镜像是固定流程：收到微信消息、写入持久状态、规范化、发送飞书、记录结果；不为每条原样消息调用 LLM。
- Codex 只在用户启动、停止、暂停、恢复、查询、身份确认或人工排障时介入。每次介入都先读 SQLite 状态，再执行一个明确事项，核验结果后反馈并写入管理记录。
- 飞书管理私聊作为 Codex 的管理入口：只处理已授权管理员的管理请求和身份确认回复；微信群中的普通消息（即使内容是“暂停同步”）不改变系统状态。
- Worker 或状态库出现新待办不会自动唤醒 Codex。若需要处理，由用户在 Codex 或飞书管理私聊中发起。
- 用户约定保持不变：不配置开机启动；进程退出后不自动拉起，用户告诉 Codex 后再检查并启动唯一实例。

## 3. 微信采集与状态

主路径使用：

```text
rion-wechat-cli tail --follow
```

同步器以 `talker + local_id/server_id` 作为消息幂等键和恢复游标。初始化时先做 snapshot，再从该游标开始 follow，避免首次监听重复发送历史消息。

补偿路径每 10 分钟运行一次 `timeline`，扫描游标之后的消息，处理 Agent、微信数据库或飞书服务短暂中断造成的缺口。高流量时必须分页读取，不能依赖单次固定数量结果。

正式版本使用 SQLite，至少保存：

- 微信群 ID 与飞书 `chat_id` 的绑定。
- 当前游标和最后成功处理位置。
- 已同步消息及幂等键。
- 媒体处理和上传状态。
- 发言人身份映射。
- 失败原因、重试次数和下一次重试时间。

媒体失败时先发送类型占位文本，不阻塞同一群的文字消息；SQLite 记录失败媒体、错误信息和本地 staging 文件，后续由人工排查，不自动反复发送造成重复。

`tail --jsonl` 在遇到部分压缩二进制消息时可能出现序列化异常；实现初期优先使用普通 JSON follow，或先修复递归 JSON 安全转换后再启用 JSONL。

## 4. 身份映射系统

本地保存以下信息：

```text
wechat_sender_id
wechat_display_name
confirmed_name
feishu_open_id（可选）
status: confirmed | pending | rejected
updated_at
```

处理规则：

- 已确认身份直接使用 `confirmed_name`。
- 未确认身份进入该发言人的待确认队列，Agent 通过飞书私聊尽快请求用户确认。
- 未确认身份不阻塞其他发言人的同步。
- 确认前继续同步：优先使用微信昵称；没有可用昵称时使用“未知发言人”。确认后只影响后续消息，不修改已经发送的历史消息。
- 微信原始 ID 只作为内部审计字段，不显示给飞书群成员。
- 支持用户随时修正姓名映射。

微信 `display_name` 可能来自备注或昵称，不能自动视为法定实名；需要实名时以人工确认映射为准。

## 5. 消息标准化与发送格式

飞书中默认显示：

```text
陈升Josh：消息正文
```

处理规则：

- emoji 原样保留。
- 链接从微信 XML 中提取标题、摘要和 URL，发送为可点击内容。
- `forward_chat` 从 XML 中提取标题、摘要、链接和必要正文，避免把原始 XML 直接发到群里。
- 系统消息转换为简洁的群事件文本；无发言人时使用系统事件名称。
- 超长正文按飞书限制拆分，或降级为文件消息。
- 不显示发送时间。
- 不显示“微信镜像”或其他额外来源标签。

飞书消息始终由 bot 发出，不能伪装成微信原发言人；姓名通过正文前缀体现。

## 6. 媒体处理

微信 `timeline` 不保证直接返回媒体路径，需要按消息 `local_id/server_id` 调用 `media --include-local-paths` 关联资源。

处理策略：

- 图片：尝试把微信 `.dat` 转换为 PNG/JPEG 后上传。
- 视频：上传 MP4，并生成飞书所需的封面图。
- 文件：上传为飞书文件消息。
- 语音、表情和无法解码的媒体：发送可读占位消息并记录失败；后续由人工排查，必要时手动补发。
- 上传前将微信本地路径复制或硬链接到项目目录内的 staging 区，满足 `lark-cli` 的相对路径限制。
- 上传成功后清理临时文件；失败媒体保留 7～30 天供 Agent 重试。
- 不向飞书发送本机微信路径。
- 媒体 XML 中可能包含密钥、令牌或过期时间，日志只能记录文件名、大小、哈希和处理结果，不能记录原始敏感字段。

图片 `.dat` 解码需要单独做技术验证；无法可靠解码时自动降级，不阻塞文字消息。

## 7. 飞书群管理

初始化流程：

1. 检查飞书 bot 和用户身份及所需权限。
2. 创建私有飞书群。
3. 将 bot 加入目标群。
4. 根据人工确认的 `open_id` 邀请成员。
5. 保存微信群 ID 与飞书 `chat_id` 的绑定。
6. 发送测试消息验证发送链路。
7. 启动由 Codex 管理的 Python worker 同步。

不能仅凭微信昵称自动邀请飞书成员。初始成员的飞书 `open_id` 和应用可见范围已完成核验；后续新增成员仍需人工确认身份后再邀请。

所有建群、邀请和发送操作都应先 dry-run，并在首次启用自动同步前由用户确认整体发送策略。正式运行后，已确认绑定范围内的镜像发送不逐条询问。

## 8. 实时性、去重与故障恢复

端到端流程：

```text
微信 tail --follow
    ↓
Agent 解析与身份确认
    ↓
SQLite 状态库去重
    ↓
媒体处理
    ↓
lark-cli 发送
```

当前正式默认微信监听轮询间隔为 10 分钟；测试和低延迟场景可在本地配置中改为 60 秒或更短。读取器以后提供稳定事件接口时，再切换为事件驱动；轮询仍保留为补偿路径。

可靠性要求：

- 至少一次处理，通过幂等键避免飞书重复消息。
- Agent 重启后从持久化游标恢复。
- 飞书不可用时文字消息进入本地待发送队列，恢复后继续发送；媒体上传失败只发占位文本并记录人工处理项。
- 消息按微信群内原始顺序尽量发送；跨媒体处理时允许短暂延迟。
- 微信数据库不可读、钥匙串锁定或进程崩溃时自动重连，并由补偿扫描修复缺口。
- 不使用 `kill -9` 终止飞书事件消费进程，避免泄漏服务端订阅。

管理流程不把飞书事件订阅当作微信消息源。飞书事件仅用于接收已授权的管理私聊；微信源消息仍以本地读取 CLI 为准。

飞书 `im.message.receive_v1` 监听的是飞书消息，不是微信源消息；第一版不依赖它触发微信同步，避免形成循环。

## 9. 测试与验收

测试必须覆盖：

- 普通文字和 emoji。
- 链接和转发消息 XML 清洗。
- 图片 `.dat` 解码成功与失败。
- 视频上传和封面生成。
- 文件、语音、表情和系统消息。
- 未知发言人触发确认。
- 重复读取不会重复发送。
- Agent 重启后能继续同步。
- 飞书不可用后的自动重试。
- 微信数据库短暂不可读后的 10 分钟补偿。
- 媒体过期、缺失和超大文件。
- 高并发下的分页、游标推进、去重和排序。
- Codex 启动前检查、暂停/恢复、状态查询、人工重启和管理记录。
- 飞书管理私聊中的未知身份确认、歧义澄清和越权请求拒绝。

验收标准：

- 正常情况下消息在几秒内到达飞书。
- Agent 重启不产生重复消息。
- 未知身份能进入快速确认流程，且不阻塞其他人员。
- 飞书发送失败不会导致消息丢失。
- 媒体失败不会阻塞文字消息。
- 姓名显示符合确认后的映射。
- 密钥、令牌和原始敏感 XML 不进入日志。
- 管理私聊只能改变明确授权的绑定和运行状态，群消息正文不能触发控制动作。

正式测试编号、测试数据和当前完成状态见《微信飞书镜像同步验收表》。

## 10. 默认假设

- 第一版同步一个指定微信群。
- 第一版只同步上线后的新消息，不回填历史。
- 飞书成员名单由确认后的 `open_id` 提供。
- 系统运行在当前 Mac 上，因为微信钥匙串和数据库读取能力绑定当前用户。
- 同步方向为微信到飞书单向同步。
- Agent 获得一次性自动发送授权；否则飞书 CLI 的写操作确认会阻断无人值守同步。

## 12. 下一迭代需求：引用消息镜像

当前版本对引用消息只做基础 XML 清洗，未建立“原消息 + 引用关系”的展示能力。下一迭代补充以下需求：

- 识别微信引用消息的被引用消息 ID、被引用发言人、引用正文和当前消息正文。
- 飞书中按以下可读格式发送，并继续保留当前消息发送人的实名：

  ```text
  当前发言人：当前消息正文
  > 被引用发言人：被引用消息正文
  ```

- 引用正文包含图片、视频、文件、表情或无法读取时，显示对应类型占位符，不把原始 XML 发到群里。
- 被引用消息已在镜像群中成功发送时，优先使用飞书消息引用/跳转关系；无法建立关系时使用上述文本回退格式。
- 被引用消息尚未同步、已过期或查询失败时，当前消息仍须同步，并在引用区域显示“原消息暂不可用”等占位说明。
- 引用消息和被引用消息分别保存稳定的微信消息键及飞书消息 ID，重启、重试和补偿扫描不得重复发送。
- 增加引用消息测试数据和验收项，覆盖普通文字、媒体、嵌套引用、被引用消息缺失及失败重试。

## 13. v0.2 实施状态

v0.2 已按确认方案落地：管理入口为 `python -m agents.manage`，网页与 CLI 共用 SQLite 管理逻辑；Profile、群绑定、人员档案和确认事项均可查询和修改。绑定级 worker 使用独立游标、文件锁、SQLite 租约和心跳，Codex 按用户指令执行启停、暂停、恢复与异常处理。

消息表已加入绑定身份、姓名快照和引用关系；媒体暂存路径按源群命名空间隔离；迁移逻辑会先保留 v0.1 游标、成功记录和身份映射。未知 ID 继续以昵称同步，并向配置管理员发送一次飞书私聊提醒；网页或 Codex 确认后只影响后续消息。引用消息在父消息已镜像时使用飞书回复，否则使用可读文本回退。

已通过单元测试、SQLite v1→v2 迁移测试、10 组绑定隔离测试和管理网页鉴权冒烟测试。真实媒体、飞书群权限和高流量场景仍需按验收表分批现场验证。

## 14. 下一迭代问题：合并转发聊天记录缺少对话内容

- 登记日期：2026-09-12。
- 状态：用户反馈，已列入下一迭代，尚未修复；具体解析原因待排查。
- 现象：微信群中发送合并转发的聊天记录后，飞书镜像只能看到链接，看不到记录内各人的发言和对话正文。
- 影响：接收者无法直接在飞书中阅读转发记录中的对话。

下一迭代要求：

1. 识别合并转发聊天记录并读取内部消息列表，按原顺序展示各条发言人的姓名与正文，同时保留外层转发人的姓名，清楚区分转发人与原发言人。
2. 原发言人有可核实的微信稳定 ID 时复用统一实名映射；只有显示名时保留原记录显示名，不凭昵称猜测或合并人员。
3. 保留文字、emoji 和链接；记录内的图片、视频、文件、表情按媒体规则处理，资源不可用时显示对应类型占位并记录失败项。
4. 支持长记录分段展示，并处理嵌套转发；读取不完整时明确标注缺失部分，避免静默丢失对话。
5. 开发时检查微信读取 CLI 提供的记录结构及附件可用性；解析失败须显示“转发聊天记录内容暂不可用”并留待排查，不能仅输出链接就视为内容同步成功。
6. 增加多人对话、未知发言人、混合媒体、长记录、嵌套转发及内容缺失的测试样例；重试不得重复发送已完成部分。

验收对应《微信飞书镜像同步验收表》T04b：飞书中可直接阅读转发记录内的发言人与对话内容，顺序正确，缺失内容有明确说明。

- 登记日期：2026-09-12。
- 状态：用户反馈，已列入下一迭代，当前实现只能发送图片占位或没有对应图片。
- 已核查现象：微信读取器的图片消息包含 `aeskey`、`cdnthumburl`、`cdnmidimgurl`、尺寸和 MD5 等元数据，但这些 `cdn*url` 值是微信资源票据/编码字段，不是可以直接交给 `urllib` 下载的普通 HTTP 图片地址。读取器的 `media --include-local-paths` 对当前样例返回空资源，说明本机尚未找到可用的图片硬链接或本地资源文件。
- 进一步核查：读取器 `access-plan` 显示数据库可读，`agent --include-status` 显示 `media_local_paths=true`；本机也有 `hardlink.db` 和配置的资源目录，但指定图片样例仍返回 `resources: []`。这说明能力开关已具备，缺的是该图片的实际本地文件/索引匹配，不能只靠给 Worker 增加一个 URL 正则解决。
- 当前代码原因：Worker 启动 tail 时关闭了媒体路径输出，图片下载函数只查找 XML 中的普通 URL 字段；没有先按 `talker + local_id/server_id` 调用读取器的媒体资源查询，也没有处理微信本地图片资源和 `.dat`/加密图片解码。因此飞书上传链路通常拿不到文件。

下一迭代建议按以下顺序实现：

1. Worker 收到图片消息后，以稳定消息身份调用 `reader media`，开启 `--include-local-paths`，优先使用读取器确认存在的本地图片路径；将文件复制到按绑定命名的 staging 目录，再用飞书 `--image` 上传。
2. 先补齐读取器的 `hardlink_db` 和 `resource_roots` 配置，并在启动前检查 `doctor`/能力状态中的 `media_local_paths`；配置缺失时给出明确诊断，不把“读取到图片 XML”误判为“图片可下载”。
3. 对本地只有微信 `.dat` 或加密图片的情况，增加受控解码器：根据图片元数据和本机授权数据库读取密钥，解码为 PNG/JPEG 后校验 MIME、尺寸、大小和 MD5，再上传；不直接把 `aeskey` 或完整 CDN 票据写入日志。
4. 本地资源不存在时，再评估由读取器负责的临时 CDN 下载接口；不在镜像 Worker 中自行拼接 `cdn*` 票据 URL。下载失败或资源过期时发送“姓名：[图片资源不可用，待人工排查]”，并保存媒体失败记录。
5. 图片上传成功后保存本地资源来源、哈希、飞书消息 ID 和重试状态；同一绑定重试不得重复发送姓名前缀或图片消息。

当前可行性判断：最稳妥的方案是先让读取器返回本地图片路径，再由 Worker 上传；如果图片从未在本机落盘，下一步需要给读取器增加受控的按消息 ID 资源获取/解码能力。仅凭现有 XML 中的 `cdn*` 票据直接下载，不能作为可靠方案。

验收对应《微信飞书镜像同步验收表》T07：覆盖本地明文图片、本地 `.dat`/加密图片、无本地资源、过期资源和飞书上传失败五条路径；成功路径必须在飞书中看到实际图片，失败路径必须有占位和可排查记录。

## 16. 下一迭代需求：管理台可维护性与长期运行优化

### 16.1 群映射和群名称

- 创建绑定时支持搜索并选择微信群、飞书群和 Profile，不要求用户手工输入稳定 ID。
- 页面同时显示群显示名和稳定标识：微信群显示 `talker`，飞书群显示 `chat_id`。
- 群显示名只用于展示，绑定和去重始终使用稳定标识。
- 增加刷新微信群名称、刷新飞书群名称和批量刷新名称功能；群改名后只更新显示名，不创建新绑定。
- 增加编辑显示名称功能，并明确区分“修改管理台显示名”和“修改真实飞书群名称”。
- 对由当前机器人创建且具备权限的飞书群，提供修改群名称和描述的操作；操作前显示目标 `chat_id`，操作后重新读取服务端名称核验。
- 微信群名称不通过只读微信 CLI 修改；如果微信侧发生改名，管理台通过重新读取结果更新显示名。
- 绑定中的源群、目标群或 Profile 不允许直接覆盖；更换时必须结束旧绑定、创建新绑定，并保留旧游标、消息和审计记录。
- 新建绑定前自动检查源群可读、目标群存在、机器人在群中、Profile 可用、目标群未被其他有效绑定占用，并显示具体失败原因。

### 16.2 飞书 Profile 管理

- Profile 页面增加重命名、健康检查、停用、删除和重新接入入口。
- 分别展示机器人状态、用户授权状态、目标群访问状态、最后检查时间和错误信息。
- `feishu-mcp` 等受保护 Profile 显示保护原因，禁止删除。
- 有有效绑定的 Profile 禁止删除，并列出受影响绑定。
- Profile 被外部替换 App ID、同名 Profile 指向新应用或授权过期时，停止受影响绑定并显示高优先级异常。
- App Secret 仍只通过 lark-cli stdin 传递，不进入 SQLite、接口响应、浏览器日志或 Git。

### 16.3 人员和身份维护

- 人员列表支持打开详情，查看实名档案、所有微信 ID、昵称、来源账号、出现群、确认状态和更新时间。
- 支持将多个微信 ID 人工关联到同一人员，也支持解除错误关联。
- 支持按 Profile 维护飞书身份，展示 `open_id` 所属 Profile，禁止跨 Profile 复用身份。
- 待确认事项支持按编号、微信 ID、昵称、群和状态筛选；确认时明确提示只影响后续消息。
- 记录姓名确认、更正、关联和解除关联的变更前后内容及操作者。
- 同名人员继续保持独立，任何自动合并都必须经过人工确认。

### 16.4 运行监控与失败处理

- 首页增加有效绑定数、运行 Worker 数、失联心跳数、待确认数、媒体失败数和同步延迟概览。
- 每组绑定展示游标、最近心跳、最近成功消息、失败数、占位数、重试数和最近错误。
- 增加绑定详情页，按消息 ID 查看发送状态、飞书消息 ID、姓名快照、引用关系和媒体任务。
- 增加媒体失败任务页面，区分微信资源不存在、资源解码失败、下载失败和飞书上传失败。
- 支持人工触发媒体重新获取、重新上传和发送占位符；重试使用原消息幂等键，不能重复发送已完成部分。
- Worker 失联时只告警和记录，不自动启动；Codex 根据用户指令执行恢复。
- 管理台显示服务启动时间、版本、数据库路径摘要和最近一次管理动作。

### 16.5 UI 和操作流程

- 用分步骤表单替换连续 `prompt()`：选择微信群 → 选择飞书群 → 选择 Profile → 预检查 → 创建绑定。
- 搜索结果显示名称、稳定 ID、成员/访问状态和当前占用状态。
- 所有危险操作提供明确确认框，显示影响的绑定、游标和目标群。
- 运行、暂停、失败、待确认和归档使用统一状态颜色；按钮根据当前状态禁用不适用操作。
- 长 ID 默认折叠，支持复制；表格支持筛选、排序、分页和按更新时间刷新。
- 页面显示数据刷新时间和服务状态；操作成功、失败和部分成功使用可读通知。
- 适配窄屏浏览器，并保留键盘操作和清晰的中文错误提示。
- 管理台继续只监听 loopback；管理令牌短期有效，不能通过普通页面内容泄露。

### 16.6 长期优化场景

- 群改名、群迁移和目标群轮换时自动刷新显示并保留历史绑定关系。
- 新增第 2～10 组绑定时减少手工输入和重复权限检查。
- Profile 授权过期、机器人被移出群或群权限变化时快速定位并恢复。
- 未知身份跨多个群出现时合并为一条确认事项，并展示所有出现群。
- 图片、视频、文件和表情失败后集中排查和人工重试。
- 消息量增长时监控积压、延迟、失败率和单组资源占用，避免单组故障影响其他组。
- Codex 新会话接管时通过管理台和 SQLite 快速读取绑定、人员和异常上下文。
- 每次版本升级先用 10 组模拟绑定验证隔离，再分批接入真实群。

### 16.7 代码与本地数据分离、首次启动引导

- GitHub 仓库只保存源代码、示例配置、数据库迁移、测试数据和不含隐私的文档；真实 SQLite、游标、媒体、日志、Profile 引用、群 ID、人员映射和本地令牌不得进入 Git。
- 提供 `.gitignore` 和启动前检查，发现数据库、日志、媒体暂存、真实配置或凭证文件准备被提交时给出阻止提示。
- 将运行目录、数据库目录、日志目录、媒体目录和 lark-cli 凭证目录作为本机数据区，支持通过环境变量或启动参数指定，不把绝对路径写死在代码中。
- 第一次执行 `python -m agents.manage serve` 或正式启动命令时，如果尚未完成初始化，进入本地引导流程，不自动启动任何镜像 Worker。
- 引导流程至少收集并确认：
  1. 当前微信读取账号和可读性检查结果。
  2. 微信群选择或 `talker`，并显示微信群名称供确认。
  3. 飞书 Profile 名称、应用名称、App ID、应用后台链接和用途。
  4. 飞书 CLI Profile 是否已接入；App Secret 只通过 stdin 交给 lark-cli，不写入项目配置、SQLite 或网页响应。
  5. 飞书助手/应用链接、开放平台后台链接、目标飞书群选择或 `chat_id`。
  6. 机器人是否在目标群、所需权限、用户授权和目标群访问检查结果。
  7. 微信群与飞书群的映射确认、同步起始策略和管理员飞书身份。
  8. 是否创建第一组绑定；首次绑定默认保存为待启动，不自动回填历史消息。
- 引导过程支持中断后继续，已完成步骤可重复检查；用户明确确认前不发送测试消息、不启动 Worker、不邀请成员和不修改飞书群。
- 引导完成后将非敏感配置写入本地配置/SQLite，并显示配置摘要；摘要只显示 Profile 名称、App ID、群名称和脱敏稳定 ID，不显示 App Secret、用户令牌或完整媒体票据。
- 提供 `setup/status`、`setup/check` 和 `setup/reset` 管理命令；重置只清除本地配置引用和绑定，不删除 lark-cli 凭证或微信数据，并要求明确确认。
- 从 GitHub 更新代码时，启动前执行数据库 schema 迁移和配置兼容检查；迁移失败保持 Worker 停止并保留原数据备份。
- 支持复制 `config.example.json` 和空数据库创建可重复的开发环境，模拟数据与真实个人数据完全分开。
- 文档明确区分“代码安装”“本地数据初始化”“飞书应用授权”“创建群映射”和“启动 Worker”五个步骤，方便新的 Codex 会话接管。

本节需求对应验收表 T26～T40，完成前管理台只视为内部原型，不视为完整的长期运营控制台。
