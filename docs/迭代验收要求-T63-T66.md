## T63：长合并转发分段与恢复

### 现有实现与缺口

`integrations/forward_records.py` 解析 CDATA、转义 XML、人员、媒体类型、链接和嵌套记录。2026-09-29 继续验收时，300 条合成记录复现逐字符拆分会切断内层记录、完整消息含标题达到 12,046 字节的问题。新增 `integrations/forward_layout.py` 按记录边界打包，完整消息含标题和续段标记不超过现有 UTF-8 12,000 字节应用预算；外层姓名只在第一段展示，后续超长单条的续段有明确标记。此为应用预算，不代表飞书服务端上限，未将 11,400 字节的预留建议默认为已确认参数。

合并转发的文章原生字段漏读已修复，11 条真实记录的飞书回读通过；新长记录分段的完整回归、部署和真实验收结果以本轮验收记录为准。原渲染计划和历史消息保持不变。超过单段预算的单个 URL 无法同时保证完整链接与消息大小，当前在任何分段外发前停止该条并保留可排查错误，不悄悄截断链接。内层媒体获取/失败任务和超深嵌套仍有独立缺口；不能由长文本分段测试代替完整 T63 验收。

### 可量化通过条件

1. 至少 300 条内层记录、正文总量超过 100,000 UTF-8 字节；正常发送和恢复后的缺失、重复、乱序数量均为 0。
2. 每段完整发送文本（含前缀及续段标记）不超过已确认的应用字节预算。当前基线为 12,000 字节，预留 5% 后使用 11,400 字节是待确认建议。
3. 能放入单段的内层记录不得拆开；单条自身超限时使用明确续段标记。去除约定展示标记后，正文、姓名、emoji 和链接与预期快照逐字一致。
4. 外层转发人与内层发言人区分明确，外层转发人只展示一次；已知稳定 ID 使用实名映射，只有显示名时保留显示名，不猜测合并身份。
5. 分别在首段、中段、末段发送中断，重启后已成功部分重复数为 0；剩余部分沿用原渲染和姓名快照，下一条新消息使用更新后的姓名。
6. 损坏、缺失记录和超深嵌套有明确占位，不静默丢弃、不直接输出原始 XML、不仅保留外层链接。整条缺失使用“转发聊天记录内容暂不可用”。
7. 内层媒体无法获取时保留正确类型占位，并按既有产品要求留可排查失败项；占位不能计为媒体上传成功。

### 测试数据与真实步骤

1. 自动样例覆盖 300～1,000 条多人对话、未知身份、中英文、emoji、长链接、混合媒体及嵌套；另含单条超过 12,000 字节、字节边界前后、空记录和局部损坏 XML。
2. 在首/中/末段注入发送失败与回执丢失，修改姓名后恢复。比对发送计划、实际段落、回执、游标及后续消息；不确定回执继续遵循 T43/T43b，不能盲目补发。
3. 真实微信群一次合并转发 100 条内层记录，包含多人和媒体；检查读取器实际结构，对照微信原记录在飞书逐条核验。用户于 2026-09-29 现场确认微信一次最多选择 100 条，因此真实验收以一份 100 条为准；300～1,000 条仅用于本机隔离模拟，不要求用户突破微信单次上限。

## T64：图片自动获取与自动重试

### 现有实现与缺口

已接入读取器 `media --include-local-paths` 和常见 XOR `.dat` 解码；失败可原位占位，人工排队任务由 `retry_media_jobs()` 消费。当前仅消费 pending/processing 队列，不等于已实现失败任务按退避时间自动重新入队；自动重试次数、调度和终止策略仍需实现/确认。真实资源缺失不能算图片上传通过。

### 可量化通过条件

1. 在声明支持的格式集合内，本地 JPEG、PNG 和可解码 XOR `.dat` 样例成功率为 100%；飞书可看到并打开实际图片。
2. 暂存/解码后校验 MIME、宽高和内容哈希；明文文件与源文件比较，`.dat` 与预期解码文件比较，不能要求解码前后字节哈希相同。飞书端如有转码，记录转换并核验可视内容，不要求平台输出字节不变。
3. 自动重试次数、每次尝试时间、下次执行时间、错误类别和最终状态可核验。建议最多 3 次重试，间隔 1、5、15 分钟；这些数值及是否含首次尝试待产品确认。
4. 暂时性故障恢复后补图恰好 1 次，姓名不重复；达到上限后保留 1 个占位和 1 条可人工处理任务，不无限循环。
5. 后续文字在图片占位成功后继续发送；失败图片不阻塞后续同步。自动补图保持与原占位的可追溯关系，回复或编辑方式待确认。
6. 重复读取、重启以及自动/人工重试竞争时，同一绑定的成功图片重复数为 0，跨绑定任务互不影响。
7. 资源缺失、解码、下载和飞书上传失败分类正确；消息、日志及管理台中密钥、完整 CDN 票据和签名参数泄露数为 0。

### 测试数据与真实步骤

1. 准备本地 JPEG、PNG、支持的 XOR `.dat`、无本地资源和过期资源；对不支持的加密格式验证明确降级，不宣称支持所有 `.dat`。
2. 注入读取失败、解码失败、下载失败、上传失败及回执丢失；按确认后的时钟策略断言次数、时间、占位、任务及回执状态。
3. 在测试微信群发送至少 5 张图片，覆盖本地已落盘和未落盘。首次失败后使资源可用或恢复上传权限，观察自动恢复及后续文字顺序。
4. 重启并重复扫描，核验姓名和图片数量不增加；重试耗尽后检查失败页仍可处理。

## T65：图片人工重试与原位补发

### 现有实现与缺口

管理台提供“重新获取并上传”，重试成功回复原占位；T54 覆盖姓名快照、回复目标和重复执行。任务尝试信息展示、并发点击、processing 崩溃恢复、过期资源处理及更细操作粒度仍需补充验收。当前失败暂存按 7 天清理，文件清理不能等同于任务或历史证据删除。

### 可量化通过条件

1. 失败项展示绑定、微信消息标识、姓名快照、媒体类型、错误、最近尝试时间及次数，均与数据库一致。
2. 单次点击、快速双击、刷新重试、两个操作并发，最终成功补图均最多 1 条；已成功任务再执行返回可读幂等结果。
3. 成功图片回复的飞书 message_id 等于原占位 ID；原姓名不重发，原占位可追溯，任务保存成功回执。
4. 再次失败时不增加占位，更新错误并保留重试入口；不得标为成功。
5. Worker 停止时点击只排队并明确提示，不隐式启动 Worker；用户后续启动后消费该任务。
6. processing 阶段崩溃后可恢复，不永久卡住、不重复已成功部分；恢复时间阈值待确认，未知回执遵守 T43/T43b。
7. 暂存文件清理后，界面明确资源状态；能否重新获取及允许处理期限按确认政策验收。

### 测试数据与真实步骤

1. 制造图片失败，记录占位回执、姓名快照和失败任务；恢复资源后在管理台重试，核对图片回复、回执和任务状态。
2. 分别快速双击、刷新后再点、并发操作，检查只补图一次；人工更名后再重试，历史姓名快照不改变。
3. 在处理中停止 Worker，恢复后核验任务；另在已停止状态点击，确认进程没有自动启动。
4. 覆盖重新获取失败、上传失败、过期资源及暂存已清理样例；检查错误可读且可继续排查。

## T66：视频号稳定链接

### 现有实现与缺口

已有 type=51 清洗及 T57 测试：完整 objectId/objectNonceId 拼接页面链接，分享 URL 回退，输出描述/作者，缺链接时占位。当前 URL 回退匹配及正文清洗仍需恶意/异常样例验证，不能只凭拼接成功认定页面稳定可用。真实双端打开行为和缺链接失败待办未完成验收。

微信复合类型 49 与 appmsg 内 type=51 属于不同层级，应在同一真实样例中核对，不能当作两个互斥消息类型。

### 可量化通过条件

1. 完整 ID 样例只展示微信群发送人、视频号描述、作者及规范页面链接；参数正确编码，反解后与原 ID 一致。
2. 飞书正文和运行日志中播放 CDN、封面、头像、升级 URL、encfilekey、token 等签名信息出现次数为 0。
3. 只有可信短分享链接时保留该链接；缺少完整 ID 且无可用分享链接时，原位显示“视频号链接暂不可用，待人工排查”，并有可追踪待办。
4. ID 缺一项、XML 损坏、作者或描述缺失时不输出原始 XML，身份不混淆。作者缺失文案待确认。
5. 重复读取、重启和补偿扫描后的重复消息数为 0；缺链接占位不阻塞后续消息。
6. 分开记录“内容清洗通过”“目标页面可打开”“飞书跨应用跳转可用”。真实页面需验证指向原视频内容，HTTP 200 或 URL 格式正确不算打开成功；客户端限制和页面失效须留证据。
7. “稳定”不能仅指验收当时可打开；复查时间窗口和客户端通过门槛待确认。未完成实测不得承诺永久有效或飞书内直接播放。

### 测试数据与真实步骤

1. 自动样例覆盖完整 ID、分别缺少一个 ID、仅短链接、仅 CDN、无作者、无描述、损坏 XML、HTML 转义和含签名参数的候选链接；加入伪造相似域名，确保不误当分享页。
2. 收集可获得的真实视频号分享 XML，核对外层 49/内层 51 和读取器分类；难以自然生成的缺字段样例在隔离测试中验证，不伪称真实样例。
3. 在授权双端测试群镜像，核对作者、描述、发送人和页面内容；检查飞书正文及脱敏日志没有禁止 URL/参数。
4. 在桌面浏览器、微信可打开的页面和飞书客户端分别打开并记录登录条件、跳转结果；按确认窗口复查。重启后扫描确认无重复。
5. 缺链接样例核验占位顺序和待办；页面实际失效样例记录为待排查，不仅凭已有链接判通过。

### T63 补充：合并转发视频子项（2026-09-29）

- 新消息中的每个视频必须拥有独立子项身份、上传回执和失败任务；相同发言人、相同视频出现多次或跨段时不能互相覆盖。
- 用外层源消息身份与内层位置查找完整本机资源；大小、摘要或源身份不符不得上传，不能把 CDN 票据误当作可公开链接。
- 视频回复到正确正文段并带内层姓名、记录序号；失败占位也必须遵循回执去重。恢复、单项重试及人工确认回执后，不重复正文/姓名/成功视频，不跳过未确认发送。
- 明确指定一条历史转发记录时才能排队补视频；旧正文计划和回执保持原样，已有失败任务可重新排队，已有成功任务不重发。
- 自动化：`tests/test_forward_video.py` 18 项通过，完整 QA 314 项通过。
- 真实样例：38 秒、1,695,436 字节视频补发后为飞书 media 消息并有封面，回复原记录；从飞书下载的文件大小和内容摘要与源资源一致。客户端播放待用户确认。其余内嵌图片及位置消息不因本次结果自动通过。

### T63 补充：合并转发图片子项（2026-09-29）

- 加密 Rec/Img 缓存须按外层消息与子项获取，解码后的 MD5 和大小匹配源资源后才能上传，不按文件名/昵称猜测身份。
- 原图可用时保留完整原图；仅可靠缩略图可用时明确标注。图片/视频混排、多图、同名同图、嵌套及跨段必须按记录次序关联正确正文段。
- 每张图独立回执和失败项。单项重试保留其他失败项、原正文和已成功媒体；旧记录须明确指定项目 messages.id 才补图。
- 未知回执在 SQLite 冻结已尝试图片的字节身份、质量及路径；缓存丢失后重建同一版本，不能暗中从原图换成缩略图。明确拒绝允许重新优选新到原图并更新待发送路径、说明质量变化。
- 自动化：`tests/test_forward_image.py` 23 项，图片+视频专项 41 项通过；完整 QA 337 项通过。
- 真实样例：已补发为飞书 image 回复，下载回来的 196,412 字节、2124×960 图片与源文件 MD5 完全相同，非缩略图，原正文和视频回执未变。用户已确认“可以正常显示”，本次内嵌图片客户端验收通过；旧百条样例及位置消息等剩余项不自动通过。
