# 普通文件消息：类型识别、完成状态与附件恢复

## 2026-10-03 发现的问题

真实 PDF 的标题约 12 秒就到达飞书，但附件没有进入上传流程。原因是发送中的微信文件使用 `appmsg/type=74`，原读取器将它归为普通 `app`，镜像程序只发送了标题；正则提取标题还把 `CDATA` 包装显示出来。这种情况不能按“附件上传慢”处理。

后续只读核验发现，同一文件完成传输时，微信会把该本地消息原地更新为类型 6，服务器消息 ID 随之改变。本次样例的群、本地编号、时间、发送者、文件名、大小与 MD5 全部一致。本地游标已经经过该消息，单纯再次读取新消息不会补上附件。原始群消息还可能在 XML 声明前包含发送者前缀，读取附件时必须沿用读取器的正文解码和去前缀方法。

## 修复后的行为

- 类型 6、74 使用结构化 XML 提取文件名、大小与摘要，正确处理 CDATA 和实体，不把文件当成纯文本标题；保留已有普通文件入口。
- 新增只读 `file-resource` 扩展，按群、本地编号、时间和服务器 ID 查找源记录，按摘要查询文件索引，再校验本地文件的大小和内容摘要。不按文件名猜测其他文件，不修改微信数据库或源文件。
- 仅旧类型 74 的请求可以附带原文件元数据进行“完成状态”核验。当前记录必须为类型 6，且同群、同本地编号、同时间、同发送者、同文件名、同大小、同非空摘要，才能接受服务器 ID 的变化。响应保留请求身份，并另行返回当前服务器 ID 与核验结果；其他身份冲突仍拒绝。
- 文件在消息专属的私有目录暂存，飞书附件保留原文件名。拒绝异常符号链接、跨目录和指向源文件的暂存路径；最大 100 MB，不上传未完成或校验失败的文件。
- 新的发送中文件尚无资源时，先保留带文件名的占位，然后最多自动重试三次；重试间隔沿用首次立即、之后 30 秒和 120 秒。空闲群也会唤醒 Worker，达到上限后转人工。队列状态与次数一起保存，中断恢复不会丢掉尚未执行的重试。
- 上传结果不确定时核验并复用暂存文件、目标和去重标识；无法核验则等人工确认，不另发占位跳过。只有明确被拒绝的上传允许更新过期的暂存路径，保留目标和去重标识。

## 已经只发送标题或附件名异常的旧记录

不自动扫描或改写历史消息。核对目标群与原标题或附件的成功回执后，先登记待办，再通过现有重试入口排队：

```bash
python -m agents.manage media-failures file-attachment --id <messages.id>
python -m agents.manage media-failures retry --id <待办编号>
```

第一个编号是项目数据库消息编号，不是微信 local_id。登记本身不发送。补发仅将附件回复到原标题消息；对于旧附件名异常的记录，回复到原附件消息。原姓名、原消息回执和游标保留，重复登记与处理不会重复上传。Worker 停止时仍需明确启动；人工排队后，可由 Codex 启动或恢复对应绑定立即处理。

旧版本曾把普通文件的暂存文件名设为“绑定编号-群摘要-消息编号.pdf”，CLI 上传时沿用该名字，导致飞书附件名与微信标题不一致。当前版本将隔离标识放在目录名中，附件文件名保留源标题；`run_lark` 转相对路径时也保留文件名。名称纠正必须有已成功发送的 `media` 回执，且其 `--file` 文件名与安全处理后的源标题不同。正确名称或回执不确定的附件不允许通过此入口重复发送。补发仍校验原文件大小和摘要，不修改源文件。
