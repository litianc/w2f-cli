# v0.4.0 M3 / M4 操作与验收

M3 把模拟文本通过真实 Mac 客户端、服务器和飞书测试群串起来；M4 将输入换为已选 Mac 微信测试群。复用 M1/M2 产品代码，操作配方见 [verify-w2f 真实文本模式](../.agents/skills/verify-w2f/features/live-text.md)。

## 三服务升级与回退

基础设施与镜像独立发布。把已审查版本的 `deploy/v040/compose.yaml`、`release.py`、`upgrade.py` 放入服务器私有候选目录，再以运维身份执行候选 `upgrade.py --root /opt/w2f-v040 --source 候选目录`。

升级器核对专用环境与管理标记、取得发布锁、备份数据库和旧配置，再替换 Compose、部署目录发布脚本和 CI 实际调用的 `/usr/local/sbin/w2f-v040-release`，并验证当前镜像。配置不合法或当前镜像验证失败时恢复原文件及入口执行权限；不重建数据卷。备份位于专用 state 的 `topology-backups`，与数据库备份一起保管。

新镜像声明 `w2f.delivery=2`；受限发布器据此以四服务运行。回退到未声明该能力的旧镜像时，将 sender 缩为零并核对旧版 API，保持原数据库/媒体卷。发布始终先停止旧 sender，避免新旧进程同时工作。受限 SSH 发布权限不变；基础设施安装须由运维完成。

基础设施准备好后，推送 `codex/v0.4.0`，由现有 CI 执行测试并自动发布已测试的镜像。待远端工作流成功，再核对公网 HTTPS 以及 app/sender 的实际版本；不可把本地测试通过当作云端发布成功。

## 真实联调

操作时固定独立用户、设备、源流和绑定。飞书应用 secret 仅写入服务器专属 `feishu_apps.json`，本地采集端只持设备上传令牌。应用与用户的归属必须一致。配置与真实消息证据均留在私有 `.v040-live`。

M3 首次只注入一条唯一标记文本。云端 `python -m cloud.verify --binding UUID --event UUID` 在 sender 容器执行，按持久部分的消息 ID 回查飞书，核对原发送应用、目标群、文本类型、未撤回状态和正文。官方接口依据：[获取指定消息](https://open.feishu.cn/document/server-docs/im-v1/message/get)。回查不改变发送状态，也不触发补发。

M4 先建立真实读取器当前上界，再让参与者向微信测试群发送新标记文本；通过有界 collect/upload 完成验证。断网恢复测试只禁止该次客户端上传进程联网，证明真实新输入可进入本地队列并在恢复后上传。首次文本及补传文本均须回查和接收人确认。

完成测试后暂停精确绑定，保留必要记录与本地恢复副本；不安装常驻采集服务、不删除群消息，也不停止其他绑定或 main 服务。

## 完成条件

- M3：同一标记关联模拟输入、本地事件、真实云端存档/部分、飞书回查和接收人可见确认；原事件重传不新增任务。
- M4：以上证据增加实际微信新消息与 Mac 读取记录，并通过有限离线后的补传；起点以前的历史未导入。
- 任一缺少接收人确认时写“API 已验证，人工确认待完成”，不能标整个阶段通过。
- Windows 真机、安装包/常驻管理、媒体及完整后台仍分开交付。
