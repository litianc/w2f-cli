## 真实绑定结果

部署前完成读取器 `sync-page` 扩展安装和 SQLite v3 迁移。绑定从 `local_id=1284` 恢复到 `local_id=1340`，固定区间 56 条均已进入终态，剩余队列为 0，Worker 心跳正常。真实飞书回读核对 72 个有回执的发送部分，目标 `chat_id`、发送应用和消息位置正确，消息位置升序。

其中 17 个表情成功上传。4 张普通图片因微信读取器没有提供本地资源，按原位置发送“图片资源不可用，待人工排查”占位并进入媒体失败页；这属于设计中的降级路径，不能当作图片已成功上传。旧版遗留的 3 个媒体失败项也仍可在页面人工重试。历史第 1285 条的旧版姓名发送曾成功但没有保存飞书回执 ID，本次将它登记为迁移证据并不重复发送；因此报告中的 72 个“有回执”部分不包含这一条可追溯但无 ID 的姓名部分。

文字回读 55 个部分中有 1 个平台显示差异：请求中的 `[奸笑]` 在飞书 API 回读为 `[坏笑]`。这是飞书表情别名规范化，正常发送和离线补发共用同一请求路径，显示效果一致；若产品必须保留字面名称，需要后续改成 Unicode/图片策略并重新验收。

验收后发现一条新的 type-51 视频号消息曾在热修复前进入飞书。已使用同一消息的回复关系补发清洗后的“描述、作者、稳定页面链接”版本；当前 Worker 已重启，后续 type-51 消息直接按 T57 规则处理。

## 已知边界与后续验收

读取器本机不存在的资源、已删除的微信历史、新格式加密 `.dat`、转发记录内独立媒体和超过 100 MB 的文件无法由恢复算法凭空还原；当前会保留顺序、占位和人工待办。大文件分片、转发内媒体下载和新加密格式适配列入下一阶段，并应分别增加真实样例测试。

管理员身份提醒只在填写已核实的 `admin_feishu_user_id` 后启用；当前配置没有填入管理员 ID，因此本次没有向任何私聊发送提醒。Worker 与管理服务均不自动开机启动或异常重启，后续由用户通知 Codex 执行恢复。

原始验收回读含真实消息 ID，仅保存于 `~/.local/share/chz-cli/recovery-acceptance-private.json` 并设置为用户可读；仓库报告不包含这些 ID。公开 GitHub 前还需清理早期 Git 历史中的现场接入文档，本阶段没有推送或重写历史。
