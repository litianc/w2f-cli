# Worker 状态查询优化

## 问题与测量

Worker 在空闲循环中约每 0.5 秒读取控制状态，发送前也会重新校验。旧的 `get_binding(id)` 先调用完整群列表，再筛选 ID；每条绑定额外读取恢复进度、成员同步设置、成员任务和群名同步设置。已归档映射同样参与这些读取。

每个查询独立打开 SQLite 连接，并执行三条连接配置 PRAGMA。21 条映射下，一轮空闲状态检查产生 107 次连接、449 条 SQL；发送前校验为 108 次连接、453 条 SQL。这里只统计管理状态读取，不含源消息读取和消息回执写入。

Profile 对账还会在名称未改变时更新应用时间戳和全部绑定。在一个应用、21 条绑定的合成场景下，每轮对账重复改写 22 行。

## 实现

1. 单群详情：在 SQL 中先按 `bindings.id` 筛选，再补该群的完整管理信息。管理接口保留成员任务、群名同步状态和恢复进度等字段。
2. Worker 状态：新增 `MirrorStore.get_worker_state(binding_id)`，一条 JOIN 同时读取当前群配置、控制状态、App ID 对应 Profile 的启用状态与当前名称。空闲循环和 `check_control` 使用该接口；没有控制记录时按已停止处理，没有应用或应用停用时发送前校验拒绝发送。
3. Profile 对账：名称变化时才更新应用；绑定名称、停用状态和缺失状态使用带差异条件的 UPDATE。无变化时不改写业务行。保持外部改名、同名应用替换、应用缺失检测和受保护应用的规则。

查询每次从 SQLite 读取新值。保留空闲控制检查周期和每次发送前校验；实名仍通过原人员接口读取。群名、成员同步线程仍按需读取完整单群详情。源消息扫描的 10 秒最小间隔、游标、分页和发送回执沿用既有逻辑。

连接继续按现有生命周期关闭，没有引入连接池或跨线程共享连接。先消除查询放大，再依据实机负载判断是否需要连接复用。

## 验证

`tests/test_worker_state.py` 新增七项回归：

- 1、10、21、100 条映射下，单群详情查询成本固定，所需管理字段完整。
- 发送前校验不展开群管理详情。
- 无变化的 Profile 对账不改写应用和绑定。
- 其他连接提交暂停、停止和应用停用后，下一次发送被阻止；恢复后可发送。
- 外部 Profile 改名立即用于后续发送，替换应用阻止旧绑定，通用受保护应用保持可用。
- 缺失 Profile 停止绑定，重复检查不重复写入。
- 控制记录缺失按停止处理，未知绑定不会读取其他群。
